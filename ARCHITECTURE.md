# Architecture

A modular monolith: a Python/FastAPI backend that owns all state and serves a compiled React UI. Ports-and-adapters only where there is a real seam: the model provider (Ollama today) and image/document ingestion.

```
frontend/  (React + TypeScript + Vite + Tailwind)     ──HTTP /api──▶  backend/agenda_first_notes/
                                                                   ├── api.py          HTTP routes; validates workspace id on every call
                                                                   ├── services.py     the only place state changes (meetings, agenda, transcript, processing, notes, approval)
                                                                   ├── history.py      explicit, audited updates to follow-ups / decisions / callings / event dates
                                                                   ├── pipeline.py     extraction → evidence validation → review round (pure functions)
                                                                   ├── evidence.py     quote location, owner support, overconfidence heuristic
                                                                   ├── names.py        member-list CSV parsing and name suggestions (pure)
                                                                   ├── agenda.py       agenda tree model, text parsing, outline for the model
                                                                   ├── segmentation.py overlapping segments with offsets + coverage
                                                                   ├── render.py       deterministic Markdown from approved tree + verified notes
                                                                   ├── prompts.py      versioned core policy + workspace profiles
                                                                   ├── llm/            ModelProvider port; ollama_provider.py, fake.py
                                                                   ├── ingest.py       image validation, OCR (vision model / Tesseract), PDF/DOCX text
                                                                   ├── jobs.py         durable single-worker job runner (rows in the workspace DB)
                                                                   ├── search.py       SQLite FTS5 per workspace
                                                                   ├── models.py       SQLAlchemy ORM (one schema, one DB per workspace)
                                                                   ├── workspaces.py   closed set of workspace ids → directories, engines, safe file paths
                                                                   ├── security.py     loopback Host, Origin allowlist, token, no-store
                                                                   ├── config.py       platformdirs data dir, global (non-sensitive) settings
                                                                   ├── repo_audit.py   pre-commit / CI content audit
                                                                   └── cli.py          serve / paths / migrate / audit
```

## Domain boundaries

| Boundary | Lives in | Rule |
|---|---|---|
| UI | `frontend/` | Talks only to `/api`. Holds no transcript in browser storage (only workspace choice and theme). |
| Application services | `services.py`, `history.py` | Every state change. Enforce the meeting state machine and the workspace. |
| Domain | `agenda.py`, `render.py`, `segmentation.py`, `evidence.py`, `pipeline.py` | Pure; no I/O; no history. |
| Model providers | `llm/` | `ModelProvider` protocol: `health()`, `list_models()`, `generate(GenerateRequest) -> str`. Ollama adapter refuses non-loopback hosts. |
| Ingestion | `ingest.py` | Validates bytes with Pillow before anything else touches them. |
| Persistence | `models.py`, `workspaces.py`, `db.py` | One SQLite file per workspace; Alembic migrations run per workspace at startup. |
| Search | `search.py` | FTS5 virtual table inside each workspace DB. |
| Export | `render.py`, `api.export_notes` | Approved revision's stored Markdown, or the live preview. |

## Workspace isolation

`workspaces.WORKSPACES` is a closed dict (`ward_council`, `bishopric`). `get_workspace(id)` validates the id and returns paths derived from it; nothing client-supplied becomes a path. Each workspace has its own SQLAlchemy engine and SQLite file, so a query cannot see another workspace's rows even by accident. Uploads, references and exports are resolved through `Workspace.file_path()`, which flattens filenames to one safe component and refuses symlinks or escapes. Jobs are rows in the workspace DB and the runner re-derives the workspace from the validated id. Model prompts are built in `pipeline.py` from exactly three inputs: the approved agenda tree, the current transcript segment, and the workspace profile string.

## Agenda representation

```json
{"id": "n3f2a9c10", "text": "Relief Society", "kind": "group", "children": [ ... ]}
```

Ids are random and stable through edits (the editor preserves them; new nodes get fresh ids). `AgendaRevision` rows are immutable once `approved_at` is set; any edit creates revision n+1 that must be approved again before processing. The model only ever sees `- [id] text` outlines and must return node ids; unknown ids become "unmapped" findings.

## Evidence model

A `Note` has `evidence: [{start, end, quote, transcript_version_id}]`. `evidence.validate_quotes` locates each model-cited quote in the segment (exact, then whitespace-tolerant) and stores global offsets into the original transcript. A note with zero located quotes is `unsupported` and never rendered. `owner_supported` requires every token of the owner's name to appear in the cited quotes, otherwise the owner is stripped (finding `inferred_owner`). `looks_overconfident` is a lexical heuristic (hedged evidence + confident text) that flags for the model reviewer and blocks convergence.

When a transcript correction creates a new `TranscriptVersion`, `evidence.revalidate` re-locates every note's quotes; anything that moved is updated, anything that vanished marks the note `stale` + `needs_review`.

Statuses: `verified`, `uncertain` (model said high uncertainty), `needs_review`, `unsupported`, `user_edited` (user text whose evidence/owner still check out), `manual_unverified` (user text without evidence). User-origin notes are never changed by the reviewer.

## Processing pipeline (`services.process_meeting`)

1. Validate: transcript exists, latest agenda revision is approved, model selected. State → `processing`. Previous model-origin notes and findings are replaced only when the new extraction succeeds (user notes kept; cancel or total failure keeps the old notes) — re-running is idempotent. On regeneration, each user-touched note (edited, moved, untagged or deleted) suppresses at most one fresh model note making the same claim, recognised by its current text or its original model text (`Note.source_text`, `source_node_id`). The match is one-to-one in passes (`services._pair_claims`): same agenda node, then same heading text across agenda revisions, then anywhere in the meeting. Identical wording that no user note claims stays. Discussion markers pair only with a marker on the same agenda item. A text re-import reuses node ids from the latest approved revision, then from the latest draft, matching by heading path, else by the same text at the same depth when that text is unique there in both trees; only new or renamed headings get new ids. While processing, transcript, agenda, note edits and delete are refused; jobs are queued, run, and recovered (meeting → `failed`) only in the process holding the per-workspace OS lock `worker.lock`. Another running copy of the app refuses to start jobs ("use that window") until the lock frees, then takes it over and fails what the previous owner left behind. `migrate` never recovers jobs. Notes on agenda nodes removed by a newly approved agenda revision are detached at approval, and coverage is reset.
2. `segmentation.segment()` splits at paragraph/line/sentence boundaries with overlap; each `Segment` tracks `status`. Coverage is persisted after every segment.
3. Per segment: `pipeline.extract_segment` → model JSON (schema-constrained) → evidence validation → deterministic findings. A failed segment is recorded, not hidden.
4. `pipeline.dedupe` merges equivalent claims from overlapping segments.
5. `services.run_review`: up to `max_review_rounds` of `pipeline.review_round` (model) + `pipeline.deterministic_checks`. Actions on model notes: remove / rewrite / move / strip_owner / clear_follow_up / add (adds require located evidence). Converged ⇔ no material (high) findings remain in a round.
6. State → `ready_for_approval` if converged and coverage complete, else `review_required`.
7. `render.render` builds Markdown from the approved tree + non-unsupported notes; placeholders depend on coverage (`Not discussed.` only when all segments succeeded). Extraction lists every agenda item the excerpt discusses, with verbatim quotes, each stored as a marker note. At render, an item with nothing rendered on or below it shows `Discussion occurred; no clear decisions or action items identified.` when a marker or a reviewer-removed note gives current evidence (not stale, from the current transcript version); otherwise `Not discussed.` (or the incomplete-coverage line). Notes the user deleted never count, so deleting the real note and then its marker is the user's explicit "not discussed". Markers are never shown to the reviewer and never render beside real notes.

Names (rules 3, 7): every capitalised word in a model note, sentence start included, must be (a) in a cited quote or the transcript line it comes from, (b) used in lowercase somewhere in the current transcript, compared by inflection stem (an ordinary word), or (c) closed vocabulary: note-writing words, titles, common note verbs, church-organisation terms and calendar words (transcripts often garble these: "steak", "elders corum"). A word right after a title (Brother, Sister, Bishop, Sis. …) is always a name and must appear capitalised in the quote or its line. Adjacent capitalised words containing a proper noun must appear together in one quote or line. The agenda is never evidence. A violation is a HIGH finding, status `needs_review`, and reviewer rewrites or adds that introduce it are rejected. Owners additionally need a full name (not a title or group) appearing contiguously in one quote.

Numbers (rule 3): every number, date or time in a model note must be stated in its evidence, as digits or number words (ten = 10, noon = 12, twenty-first = 21); otherwise HIGH, and rewrites or adds that introduce one are rejected.

Commitments (rule 6): hedged or question-only evidence makes confident wording overconfident, unless the quotes contain an answer or commitment outside a question whose own clause is neither hedged nor negated.

Placement (rule 1): notes and markers go under an agenda item only when the discussion is about it; group-level discussion goes on the group heading; otherwise the note stays unmapped. A deterministic relevance check requires a content word of the item's heading (or an ancestor's, names excluded) in the quotes, their lines or the 250 characters before them; otherwise "May not belong under …" (HIGH for markers and leaf notes, LOW for group notes). A group note matching a child heading gets a LOW "May belong under …". Leaves render only from their own evidence.

Quotes: verbatim modulo whitespace, case, Unicode and dashes, on word boundaries judged against the full transcript. Fallbacks: crosstalk speaker labels and bracket tags between fragments may be skipped (never spoken words), and a quote stitched with "..." is split into fragments that must all be found in order. Each evidence item stores its transcript line as `context`.

## Member-list name suggestions (confirm-first)

One member list is shared by both workspaces (maintainer decision 2026-11-08; CSV columns: preferred name / full name / spouse / callings with sustained dates). It lives in `<data>/members.sqlite3`, outside both workspace databases, with the same pragmas (WAL, `secure_delete`, hidden SQL parameters); its one table is created if missing, without Alembic (`shortcut:`). Routes `/api/members` (GET/POST/DELETE) take no workspace id; suggestions and confirmations stay per workspace and meeting. An import replaces the list (new member ids; a rejection whose id is gone matches by name), "Delete member list" purges it. `names.suggest(transcript, tree, members, decisions)` is pure and deterministic: it finds titled words ("Brother Tarn"), capitalised name-like runs (a lone word only when it does not start a sentence) and lowercase pairs starting with a member's first name or nickname ("bob oss"), with a possessive "'s" stripped, and scores them against first/preferred names, a small nickname table and surnames (Soundex + difflib). Only clear fits are suggested (rule 12; maintainer report 2026-11-08 of junk matches such as "Honestly", "Europe", "Air"): a titled word the surname at 0.8; a lone word a first, preferred or surname exactly, never a sound-alike; "First Last" the first name at 0.85 (a nickname counts 0.9) and the same member's surname at 0.8; a lowercase pair the first name exactly or as a nickname and the surname at 0.85 (a rhyme such as "bob boss" for Ross no longer qualifies). It adds context: the organisation of the agenda item the mention seems to sit under (heading words found shortly before it; context only, never evidence) or mentioned nearby, and a spouse mentioned nearby. Candidates rank by name likeness alone; context (agenda item, a capitalised organisation name nearby, a spouse named nearby outside the mention itself, a Sister/Brother title against gendered callings) only orders candidates with equal name scores, and ties say how many members share the surname. For a titled mention a spouse named nearby counts for neither of a couple who are both candidates. Each suggestion shows the heard text, how often it occurs (a confirmation covers every occurrence) with up to three transcript lines, the agenda item, up to three candidates with callings (dates are display-only) and a plain-English reason. Nothing is resolved automatically: the user confirms or rejects a current suggestion (`name_confirmations`, per meeting, by member id, one confirmed name per heard text, audited, deletable).

On the next generation the prompts carry a short "user-confirmed names" block (heard text → name only; never the list, callings or dates), and the name check accepts only a whole confirmed name form (full or preferred, never a part such as "Ross" or "Sister Ross"), and only in a note citing a quote that contains the heard text; the quote's surrounding line does not count (rule 12). Whether a note relied on a confirmation is stored when its status is derived (`notes.name_confirmed`, also in the approval snapshot), never computed live: such notes are shown as "Name confirmed by you", never "Source verified", and history rows proposed from them have origin `user`. Removing a confirmation or editing the transcript re-derives the notes' status and re-runs the deterministic checks, so a name only the removed confirmation licensed becomes a blocking finding. Deleting the member list also deletes the "not this person" answers in both workspace databases (each in its own) and redacts the audit payloads of every answer except the confirmed names, which stay with their meetings; the shared store's WAL is checkpointed after import and deletion, and each workspace's after deletion (a warning is shown if it stays busy). Owners still need the name inside a quote. The member list never reaches logs, jobs, exports, search or any provider other than the local one, and is never evidence of callings (rules 3, 8). `.gitignore` and the repo audit refuse member/roster/directory/ward-list CSVs and spreadsheets (every letter case), files with the member-list heading or several "(5 Jan 2025)" sustained dates outside SYNTHETIC tests in the test folders, and UTF-16 files are checked too.

Agendas may misspell names too. `names.agenda_people` finds person-name spans in headings (two or three adjacent capitalised words that are not note, organisation or calendar vocabulary; one-word and titled names are skipped, `shortcut:`), and compares them with the member list. A name written as a member's own (as listed, or a nickname of the first name with the exact surname: "Tom Cope" is Thomas Cope) is exact, and then no other member is considered; otherwise by spelling (each of first name and surname at least 0.75 alike). A three-word run whose last two words score at least as well is shortened ("Meet Matt Smith"), unless the whole run names a member (a middle name); a trailing plural or possessive "s" stays outside the name when that scores better ("Tim Copes calling"). (1) While the agenda is a draft, `POST …/agenda/name-check` (the editor's unsaved tree; read-only, nothing for an approved agenda) returns names that name no member exactly but spell one member clearly better (by at least 0.05) than any other; equally close members produce nothing, so the agenda never decides who is meant; the agenda step shows "Agenda says 'Sindy Jones' — member list has 'Cindy Jones' (Primary Teacher). Fix spelling?". Fix spelling edits that span of the draft heading exactly as typing in the editor would; Dismiss hides it; exact names produce nothing. (2) Transcript suggestions: a member whose own name the agenda writes gets "On the agenda as …" and a context boost that only orders equal names; a member the agenda only closely spells gets the display text "may be on the agenda as … (spelled differently)" and no boost. The name score is the better of the likeness to the member's spelling and to the agenda's, the latter capped at the agenda's own likeness to the member, and "matches the agenda's spelling" is said only for the member's own name. (3) A confirmed name whose member an approved heading writes exactly and unambiguously (`names.agenda_links`; a misspelt or two-person name links nobody) is shown in the prompt as `"heard" -> Name (agenda item: 'heading')` (heading whitespace normalised), with the rule that this is not evidence that the item was discussed; in `placement_findings` a note whose cited quote says the heard text gets a LOW instead of a HIGH "May not belong under" there (a name is no topic), and a discussion marker never does (rule 1). The name check is unchanged: the agenda's misspelling is never a confirmed form, and a confirmation never marks an item discussed.

## Historical reconciliation (`services._propose_history`)

On approval, an immutable `NotesRevision` snapshot is written, then for each live note: `follow_up` → `FollowUp(status=proposed)` + `FollowUpEvent`; `decision`/`proposed_decision` → `Decision(confirmed|proposed|unverified)`; `calling_event` → `CallingEvent`; `date` → `ScheduledEvent(event_date=None)`. Each carries `origin` (transcript|user: user only when the user changed text, owner or evidence) and the evidence, and writes an `AuditEvent`. Only notes on nodes of the approved tree are proposed. On re-approval, a history row stays with its own note when that note is still rendered; otherwise it takes over one note making the same claim through the same one-to-one passes (same node, then same heading text, then anywhere), and its `source_note_id` moves to that note, so regeneration, refiling and heading renames do not duplicate rows. The latest approved revision holds the facts: a row whose note is gone from it becomes `unverified` with an audit event (a follow-up only while still `proposed`, also with a `FollowUpEvent`; a decision, calling event or scheduled event only if the user never changed that row in the inbox; a row created from a note the user reworded is not protected), and returns to its previous status if the note comes back. Nothing else existing is modified; rows are never deleted. Users then confirm/edit in the inbox (`history.py`), each change appending `FollowUpEvent`/`AuditEvent` rows; date changes create a superseding `ScheduledEvent` instead of overwriting.

Undiscussed agenda follow-ups (Case B) are detected lexically by `services.undiscussed_agenda_follow_ups`, shown in the review panel, and only enter the final follow-up list when the user ticks them (`Meeting.carry_forward`). Historical items absent from the agenda (Case C) never touch the notes.

## Rendering

`render.render(title, meeting_date, tree, notes, coverage_complete, extra_follow_ups)` is pure and tested against golden strings. Rules: exact node text, two-space nesting, notes as child bullets, `[Follow-up]` then `[Owner: …]` at the end, one placeholder per undiscussed leaf or per fully-undiscussed group (children listed bare), then exactly one `Next Meeting – Follow-Up Items` flat list (deduped, carry-forwards appended, or `No follow-up items identified.`).

## Meeting state machine (`models.TRANSITIONS`)

`draft → agenda_imported → agenda_verified → transcript_added → processing → {ready_for_approval | review_required | failed} → approved → archived`, with explicit back-edges for edits (`agenda_imported` on agenda change, `transcript_added` on transcript change or cancel, `ready_for_approval` on reopen). `services.transition()` rejects anything else. Approval from `review_required` is allowed only once no unresolved high-severity findings remain.

## Database schema (per workspace)

`meetings`, `agenda_revisions`, `agenda_images`, `transcript_versions`, `notes`, `notes_revisions`, `review_findings`, `jobs`, `follow_ups`, `follow_up_events`, `decisions`, `calling_events`, `scheduled_events`, `name_confirmations`, `audit_events` (append-only, except that deleting a meeting redacts that meeting's payloads and deleting the member list redacts name-answer payloads; `secure_delete` on, WAL truncated), `reference_documents`, and the FTS5 virtual table `search_index(entity_type, entity_id, meeting_id, meeting_date, status, title, body)`. The shared `<data>/members.sqlite3` holds only `members` (migration 0007 drops the old per-workspace table). Column details: `backend/agenda_first_notes/models.py`. Migrations: `backend/alembic/versions/`.

## Jobs

`jobs.py` runs a single worker thread (models run sequentially to conserve memory). A job is a row with `status/progress/message/cancel_requested`; the processing loop checks `cancel_requested` between segments. `enqueue` refuses a second active job for the same meeting and kind. At startup, jobs left `queued/running` are marked failed with a retry hint.
